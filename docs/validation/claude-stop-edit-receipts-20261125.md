# Claude 停止、历史编辑与消息回执验收（2026-11-25）

## 用户反馈

用户在新安装的版本里遇到三个问题，并要求 Harness 自己判定结果，不让用户去原版 CLI 核对：

1. 发出消息或交互后出现“回执”类提示（“正在确认消息送达结果”“查回执”“已人工确认”）。
2. 发出消息后点击停止，会话里多出一条用户气泡 `[Request interrupted by user]`。
3. 编辑已发出的消息再次发送出现异常。

## 根因与证据

服务端回执文件的统计只含状态与错误类别，不含正文。最近 72 小时共 398 条回执：395 条完成，1 条未知，2 条失败。

| 现象 | 根因 | 证据 |
| --- | --- | --- |
| 编辑失败后页面卡在“正在确认送达”，并弹出红字 `notice is not a function` | 失败路径 `draft-restore.js` 调用了 `notice` 但没有导入；页面里 `id="notice"` 的元素会成为同名全局变量，所以运行时报“不是函数”而不是“未定义”。异常发生在清除待确认记录之前，锁定留了下来 | 用户截图；新增“未声明名字”静态检查后另发现 `events.js` 漏导入 `renderSidebar`、`session-tools.js` 的 `options` 越界引用，一并修复 |
| 编辑报“原生会话仍在其他 CLI 中打开，未修改历史” | 旧 `stop_cli` 发出停止请求后立刻关闭写端，连接端随之断开，Harness 误以为 CLI 已退出就去核对持有者；真实 CLI 此时仍在收尾，登记文件还在 | 真实 CLI 2.1.330：关闭输入后登记文件 0.05–0.56 秒消失，进程 0.45–1.06 秒退出；服务端回执里北京时间 11:11 的失败回执正是这条错误 |
| 点击停止约 62 秒后提示“送达状态未知，请查看原生会话” | 控制请求等回执的上限是 60 秒；那次 CLI 已在原生记录里写下中断标记，回执却没有到达，停止留成“未知”，还让用户去原生客户端核对。该次 CLI 为何没回执没有复现 | 回执文件里北京时间 11:08 的未知回执；真实 CLI 在流式输出与 Bash 执行两种场景下 interrupt 回执均约 0.01 秒 |
| `[Request interrupted by user]` 显示成用户气泡 | CLI 2.1.330 起工具结果与后续记录之间会写 `attachment` 记录，中断标记的 `parentUuid` 可指向附件；读取器没有穿过这些记录，识别不出它属于被中断的回复。桌面应用（`entrypoint=claude-desktop`）写入的同类标记同样没有被识别 | 在真实 87 MB 会话文件上验证：标记已识别为中断，不再计为真人消息 |

## 改动

**停止**（`claude_sdk/peer.rs`、`host.py`、`claude.rs`、`lib.rs`、`composer.js`）

- 停止请求发出后，CLI 回执、会话转为空闲、进程退出任一出现即成功；最多等 8 秒。
- 8 秒内两者都没有，向宿主发 `host_kill`：宿主先 SIGTERM，5 秒后补 SIGKILL，最多等 15 秒；成功后返回 `forced: true`，页面提示“Claude 没有响应停止请求，已强制结束它的进程；会话已保留，可以继续发送”，下次发送用 `--resume` 接上。
- Claude 的停止成功提示不再写“清理后台终端”（那是 Codex 的行为）。
- 停止没有得到确认时，提示“停止请求没有得到确认，可以再点一次停止”，不再套用“请查看原生会话”。

**历史编辑**（`peer.rs`、`claude_shared.py`）

- 停止自己的 CLI 时保持连接，直到宿主报告 CLI 真正退出（最长 40 秒，超时才强制结束）；同一会话的启动与停止串行。
- 读取器核对持有者时额外容忍至多 5 秒的登记清理间隙；别的应用持有会话时仍拒绝，历史保持不变。
- 宿主 `host.py` 收尾超时后先 SIGTERM，再过 5 秒补 SIGKILL，不再无限等待。

**中断标记**（`claude_shared.py`）

- 沿 `parentUuid` 向上穿过未进入正文的记录（最多 64 跳），找到被中断的回复。
- 入口白名单为 `sdk-*` 与 `claude-desktop`，其余元数据条件不变，用户自己输入同样文字仍是普通消息。

**消息回执**（`claude_queue.rs`、`claude.rs`、`pending.js`、`pending-state.js`、`composer.js`）

- 服务端对 `sending` / `unknown` 的消息：会话空闲（没有执行、没有等待用户）且没有任何原生接收记录时结案。`unknown` 满 45 秒、`sending` 满 120 秒；结案后移出队列，记为“没有送达”，不再挡住后续发送；原生记录晚到时以接收记录为准。
- `sendState` 新增 `deliveryState: notDelivered`；页面据此按失败处理，恢复输入、解除锁定，仍不自动重发。
- Claude 会话的发送与历史编辑待确认时，横幅只显示“正在确认消息送达，确认后会自动更新，无需操作”，不提供“查回执”“已人工确认”；超过 3 分钟仍无结论才出现“放弃等待”，放弃会把内容恢复到输入框。
- Codex 会话以及目标、队列、分支、压缩等其他回执保持原有人工核对入口。

**静态检查**

- `check-harness-assets.mjs` 新增“未声明名字”检查（`harness-undeclared-names.mjs`），防止同类漏导入再次出现。

## 真实 CLI 验证（测试实例，Claude Code 2.1.330）

| 项目 | 结果 |
| --- | --- |
| 流式输出时 interrupt | 回执 0.01 秒，result 0.02 秒，idle 帧 0.03 秒，中断标记 `entrypoint=sdk-cli` |
| Bash 工具执行中 interrupt | 回执 0.01 秒，result 与 idle 帧 0.03 秒 |
| 关闭输入后退出（无 MCP） | 记录最后写入 0.05 秒，登记文件消失 0.05 秒，进程退出 0.45 秒 |
| 关闭输入后退出（带收尾要 6 秒的 MCP 服务） | 登记文件消失 0.56 秒，进程退出 1.06 秒，CLI 不等该服务 |
| 存活 CLI 上直接 `rewind_conversation` | 回执 0.01 秒，再问一轮上下文确实回退（含第一轮回复、不含被回退的第二轮） |

存活 CLI 上回退可行，但读取器的编辑锁、历史头与持有者核对要一并重做，本次仍采用“先让自己的 CLI 退出再回退”的交接流程。

## 自动化测试

结果见下文“结果”一节。新增覆盖：

- `peer.rs`：停止成功、会话空闲即成功、CLI 不响应强制结束、CLI 拒绝停止强制结束、编辑等待 CLI 真正退出（用变异验证：恢复旧的立即关闭写端后该用例失败）。假宿主改为贴近真实连接端：写端关闭即断开，CLI 收尾用独立计时器模拟。
- `claude_queue.rs`：结案条件（只结案超时的 `sending` / `unknown`，会话非空闲或压缩命令不动）、记录上限、`sendState` 返回 `notDelivered` 且不再挡住后续发送、原生记录晚到仍以接收记录为准、强制停止回执透传。
- 读取器 Python 测试：穿过附件的中断标记、`claude-desktop` 入口、父链上限、用户同文消息不误判、持有者短暂延迟。
- 网页：回执未知后服务端结案时自动恢复输入、不重发；标识不匹配时不结案；Claude 横幅无人工核对按钮，3 分钟后才出现“放弃等待”，Codex 横幅不变；侧边会话已读回调转交。

## 真实宿主与 CLI 联调（强制结束与停止收尾）

用真实 `host.py` 和真实 CLI 模拟对端的 `host_attach`、`initialize`、`host_stop`、`host_kill`，保持写端打开：

| 场景 | 结果 |
| --- | --- |
| `host_stop`（无 MCP 服务） | `host_exit` 在 0.61 秒到达；此刻 CLI 进程和登记文件都已消失，退出码 0；连接 0.92 秒后关闭 |
| `host_stop`（带收尾要 6 秒的 MCP 服务） | `host_exit` 在 1.24 秒到达；此刻进程和登记文件已消失；连接 1.56 秒后关闭 |
| `host_kill`（CLI 被 SIGSTOP，对 SIGTERM 和关闭输入都没有反应） | `host_exit` 在 5.50 秒到达，退出码 -9（SIGKILL）；连接 5.81 秒后关闭，在对端 15 秒上限之内 |

由此确认：对端保持写端等待 `host_exit` 时，收到退出报告的那一刻 CLI 已经退净，随后读取器核对持有者不会再看到它。
