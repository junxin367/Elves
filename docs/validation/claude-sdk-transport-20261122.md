# Claude Agent SDK 传输真实环境验收（2026-11-22）

本记录对应 Claude 会话从“daemon 后台任务 + 终端画面识别”改为“Claude Agent SDK 的 stream-json 控制协议 + WSL 内宿主”，以及随之而来的会话占用与“在 WSL 打开”行为。实现与进程分工见[Harness 架构](../harness-architecture.md#claude-执行引擎)，产品行为见[远程接入指南](../product-standards/sessions/remote-access-guide.md)和[会话被其他应用持有](../product-standards/core/product-behavior.md#会话被其他应用持有)。

验收分两轮：第一轮用发行版内的模拟上游把传输层的 28 个检查点跑通；第二轮上游替换后，用真实的 gpt-6.1-sol 重新覆盖全部场景，并补测会话占用、在 WSL 打开和长时间等待审批。下面的结果以第二轮为准。

## 验收环境

- Windows 侧：Harness 调试构建（`cargo test` 进程）经真实的 `wsl.exe` 驱动测试实例 `codex-elves-claude-test`（用户 `elves-test`），Claude Code 2.1.329，登录 shell 时区 `America/Los_Angeles`。
- 配置隔离：用 `CLAUDE_CONFIG_DIR` 指向发行版内的临时目录，经 `WSLENV` 传入所有 `wsl.exe` 子进程；实例自己的 `~/.claude` 没有被改写。隔离配置的 `settings.json` 由实例的设置派生（保留 `model: gpt-6.1-sol`、`availableModels`、`modelPicker` 和上游密钥），只把上游地址结尾的 `/v1` 去掉，权限默认模式设为 `default` 以便稳定触发审批。验收后该目录（含密钥副本）已整体删除。
- 模型与上游：会话里选择 `gpt-6.1-sol`，请求经测试环境的真实上游返回；CLI 会话记录里助手消息的 `model` 字段为 `gpt-6.1-sol`。

## 测试实例的上游地址带 `/v1`

测试实例 `settings.json` 的 `ANTHROPIC_BASE_URL` 是 `https://cpahd.faibak.com/v1`。Claude CLI 会自己追加 `/v1/messages`，请求因此变成 `/v1/v1/messages`，上游返回 404，CLI 报“There's an issue with the selected model (gpt-6.1-sol)”。基址去掉结尾的 `/v1` 后，同一个模型、同一个密钥立即正常。这是该实例配置本身的问题，与本次改造无关；本次验证没有修改实例的配置文件，实例当前仍是带 `/v1` 的原样，需要使用者自行修正。

## 会话占用与“在 WSL 打开”（真实 CLI）

| 场景 | 结果 |
| --- | --- |
| Elves 自己的宿主和 CLI 运行期间（空闲、等待审批、执行中） | 不被当成别的应用；占用状态依次为“Elves 空闲持有”“Elves 执行中” |
| 执行中请求关闭占用 | 被拒绝，提示“会话正在执行任务，无法关闭占用…”，不打断任务；点停止后恢复空闲 |
| 只读准备打开 WSL（描述会话、返回占用状态） | 不关闭任何进程，WSL 参数为 `--resume <原生会话 ID>` |
| 确认后关闭 Elves 的占用 | CLI 与宿主退出，原生登记清空，占用状态变为“无人持有” |
| 另一个真实 CLI 对同一会话 `--resume`（模拟终端里打开） | 约 1 秒内被识别；线程读取返回 `externalWriter` 并置只读，占用状态为“别的应用持有”；发送被拒绝，提示“已在另一个应用中打开”，不留下任何内容；请求关闭占用同样被拒绝 |
| 终端里的 CLI 退出后 | 提示解除，线程恢复可写，发送正常 |

## 真实环境里发现并修复的问题

第一轮（模拟上游）发现的三个问题已修复，细节如下，第二轮在真实上游上复测通过：

1. **宿主连接端丢帧**：`host.py` 用带缓冲的 `sys.stdin.buffer.readline()` 读第一行，Harness 紧接着写入的 `initialize` 与 `host_attach` 一起进了缓冲，转发线程改用 `os.read(0)` 直读，这一帧丢失，CLI 永远没有回应，白等 60 秒。已改为直接从文件描述符读取并转交多读到的字节，对端也必须先等到 `host_hello` 才写第一条请求。
2. **SDK 中断标记被当成新一轮**：`interrupt` 控制请求写下的 `[Request interrupted by user]` 行没有 `interruptedMessageId`，既有规则不认。读取器现在只在同时满足 `entrypoint` 为 `sdk-*`、文字完全一致、不带真人输入属性、与被中断提示共用 `promptId` 时补充中断证据。
3. **宿主永不收尾**：被打断的命令以 `command_lifecycle: cancelled` 结束，宿主只把 `completed` 当终态。现在除 `queued`、`started` 之外的状态都视为终态，且会话空闲时清空进行中记录。

第二轮（真实上游和占用流程）新发现并修复的问题：

1. **宿主在 Harness 沉默 60 秒后丢掉连接**：`host.py` 对 Harness 连接设置了 `settimeout(60)`，同时限制了读取和发送。Harness 在等用户批准审批、或任务长时间没有输出而一直没有写入时，读取 60 秒超时被当成断线，宿主丢掉连接；网页随即显示会话空闲（`sessionAlive` 为假）、审批请求消失，CLI 却仍在等待回答。真实模型做计划时先起子代理再提交计划，用时超过一分钟，第一次完整联调因此卡在“计划确认请求没有出现”；模拟上游的场景都在几秒内答复，没有暴露。现在只用 `SO_SNDTIMEO` 限制发送方向，读取保持阻塞。回归测试 `SdkHostConnectionTests` 在旧实现上失败（读取超时为 60 秒）、修复后通过，并在真实联调里加入“审批等待 75 秒后再批准”的步骤。
2. **占用判断只看内存里的连接**：Harness 刚重启、尚未接回宿主时，宿主里的 CLI 仍在执行，却会被判成“无人持有”，用户可能被允许直接打开 WSL。现在以原生进程登记为准：登记里有 Elves 自己的进程时，空闲且连接在线才算“可关闭”，其余按“执行中”处理。
3. **读取器沿用了旧版的启动方式**：读取器进程启动时带 `CREATE_BREAKAWAY_FROM_JOB` 并关闭 `kill_on_drop`（旧版代码里的设置）。在不允许脱离作业对象的环境（例如 `cargo test`）里，`wsl.exe` 启动报“拒绝访问（os error 5）”，占用核对因此失败。新版的读取器只服务当前 Harness，Harness 退出时随之收尾，已改回与其他 WSL 进程一致的启动方式。

## 其他事项

- 失败点的诊断日志：对端在宿主无响应、CLI 初始化失败、宿主退出或拒绝、回执超时时写 `claude.sdk.*` 诊断记录（只含事件名、原生会话 ID 前缀和简短原因，不含消息、配置和 CLI 的 stderr）。
- 真实模型的行为差异：计划模式下 gpt-6.1-sol 有时先起 Explore 子代理并安排延后唤醒，再经 `ToolSearch` 取出 `ExitPlanMode`；对端按 `can_use_tool` 请求处理，不依赖具体路径。`sleep` 这类被 CLI 判为只读的命令不需要审批，长命令场景用需要审批的前台命令（`python3 -c "import time; time.sleep(100)"`）验证。
- 未实机覆盖：实例默认的 `auto` 权限模式（需要真实模型处理分类器请求；该上游不兼容计费的分类器请求，CLI 会提示）、多实例并发、空闲 10 分钟回收（只有单元测试）。
- 本次实机测试依赖特定发行版和发行版内的临时配置，没有入库；验收后发行版里的隔离配置、测试项目、外部持有者脚本和遗留宿主都已清理。
