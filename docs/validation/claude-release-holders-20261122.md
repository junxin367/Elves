# “关闭其他占用”与被占用时的 Open in 真实环境验收（2026-11-22）

本记录接在[Claude Agent SDK 传输真实环境验收](claude-sdk-transport-20261122.md)之后：使用者编译试用新版后提出两点，一是占用提示只有“重试”，不知道是谁在占用时无法继续使用；二是 Claude 会话被占用时 Open in 入口消失。实现见[会话被其他应用持有](../product-standards/core/product-behavior.md#会话被其他应用持有)和[Harness 架构](../harness-architecture.md#claude-执行引擎)。

## 验收环境

测试发行版 `codex-elves-claude-test`（用户 `elves-test`），Claude Code 2.1.329。用 `CLAUDE_CONFIG_DIR` 指向发行版内的临时配置，只用真实上游创建原生会话，没有改动实例自己的 `~/.claude`；验收后临时配置（含上游密钥副本）、测试项目和脚本已整体删除，没有遗留 `claude daemon` 或宿主进程。持有者全部是真实 CLI 进程，不是模拟。

## 关键发现：旧版 daemon 任务不能只结束进程

`claude --bg`（旧版 Elves 的后台任务）的进程树是 `claude daemon run` → `bg-pty-host` → `bg-spare`，登记文件 `sessions/<pid>.json` 记的是 `bg-spare`，`kind` 为 `bg`，带 8 位 `jobId`。

- 对登记的进程发 SIGTERM：1 秒内退出、登记清除，但约 15 到 20 秒后守护进程重新拉起一个 `--resume` 进程并再次登记同一个会话。只结束进程的“关闭其他占用”会在用户刚继续使用后又被占回。
- `claude stop <jobId>`：不到 1 秒停止，任务标记为 `stopped`，之后 38 秒没有任何重启，临时守护进程自行退出。

所以服务端对 `kind=bg` 且带任务 ID 的持有者先执行原生 `claude stop`，其余持有者才发信号。`claude stop` 与读取器必须使用同一份 `CLAUDE_CONFIG_DIR` 环境：第一次验证时读取器环境里没有它，`claude stop` 找不到任务而失败，退回信号后任务被重新拉起，复现了上面的现象。

## 覆盖结果

| 持有者 | 关闭方式 | 结果 |
| --- | --- | --- |
| 旧版 daemon 后台任务（`claude --bg --resume <会话 ID>`） | `claude stop` | 读取器层 0.9 秒；经 Rust 服务全链路 1.8 秒；35 秒与 40 秒后均无持有者，没有被重新拉起 |
| 终端里的交互式 claude（pty，`kind=interactive`，`entrypoint=cli`） | SIGTERM | 0.7 秒退出，退出码 143，登记清除 |
| SDK 方式的 CLI（stream-json，stdin 保持打开，`entrypoint=sdk-cli`） | SIGTERM | 读取器层 0.6 秒；全链路 0.61 秒，退出码 143 |

全链路（Rust 服务 → WSL 读取器 → 真实进程）另外确认：

- 被占用时线程读取返回 `externalWriter=true`、`readOnly=true` 和 `externalHolders`，其中只有 PID、类型和入口，没有命令行、目录或环境。
- 远程设备授权调用 `releaseExternalHolders` 被拒绝（403），读取器没有收到请求，持有者仍在。
- 本机授权调用后持有者退出，再次读取回到可写、不带 `externalHolders`。
- 交互式 claude 在隔离配置里首次启动会先弹“检测到环境中的自定义 API Key”确认框，默认选“否”；验证时先应答“是”才会登记会话。这是验证方法上的前置，不影响功能。

## 自动化测试

- Python 读取器测试 84 项通过：新增 11 项真实子进程用例，覆盖 SIGTERM 退出、忽略 SIGTERM 后 SIGKILL、只结束登记为该会话的进程、Elves 自己的宿主不受影响、启动标识变化后不发信号、`claude stop` 先于信号、`claude stop` 失败仍结束进程并上报、登记里的任务 ID 不是 8 位十六进制时不进入命令行、终端持有者不空等后台任务、已退出但未被回收的僵尸进程不算持有。
- Rust 新增 3 项：外部持有者清单不泄露进程细节且最多八项；本机授权结束外部进程且不动 Elves 自己的进程；远程授权 403、进程不肯退出时返回“仍有 N 个进程没有退出”。`desktop` 边界测试补充能力声明、远程直接请求 403、本机非法载荷 400，以及合法请求分别进入 Claude 引擎和被非 Claude 会话拒绝。
- 网页测试新增 8 项：按钮仅在本机 Claude 会话显示并排在“重试”右侧；危险确认框写明进程类型、PID 和影响；确认后进入“关闭中…”且不重复提交；取消不发请求；服务端拒绝时给出原因并重新读取；关闭成功后重新读取失败时不报成“关闭失败”；弹窗期间切换会话或连接后旧确认不生效；占用时 Open in 入口保留，设备只读、子代理和非占用原因的只读仍隐藏。
- 用项目样式表渲染占用横幅的静态预览（1000px 和 480px 宽），两个按钮并排不溢出，处理中状态宽度不变，Codex 与远程设备只显示“重试”。

## 未覆盖

- 在 Windows 本机客户端里实际点击“关闭其他占用”和 Open in：本次没有安装新构建，需要使用者重新编译后确认。
- Elves 自己的宿主与外部持有者同时存在：Elves 的进程按脚本路径排除，由 Python 用例覆盖，没有在真实环境里同时启动两者。
- 一个会话同时有两个以上不同任务 ID 的 daemon 任务：读取器逐个 `claude stop`，单个任务的上限是 20 秒，没有构造这种场景。

## 后续调整：各端一样提供（同日）

使用者随后要求“关闭其他占用”在网页、手机和 Android 上也显示，不做特殊处理。上文“远程设备授权被拒绝（403）”是调整前的验证事实，调整后改为：

- 服务端不再按设备拒绝；`releaseExternalHolders` 能力对所有设备声明为真（保留能力声明，是为了让内置旧网页包连到不认识该动作的旧后台时不显示会 404 的按钮）。只读访问仍由统一入口返回 403，请求仍只接受会话标识，非 Claude 会话仍返回 409。
- 自动化：Rust 用例改为远程与本机授权都能结束外部进程，进程不肯退出时两种授权得到同样的 409；`desktop` 边界测试改为本机与远程请求同样校验载荷并路由；网页测试新增远程传输下的显示和提交用例，以及旧后台不声明能力时隐藏按钮的用例。
- 说明：已配对的远程设备本来就能给 Claude 会话发送消息并批准命令，在 WSL 里执行任意操作，结束一个 `claude` 进程没有扩大权限范围。
- 未在真实环境重复：进程结束与 `claude stop` 的实机结果与设备类型无关，沿用上文；没有再用真实远程设备点击。
